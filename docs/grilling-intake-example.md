# 分轮追问如何改变建议：自编演示

这是为解释新流程编写的模拟对话，不是真实用户事实，不是模型前后 A/B 测试，也没有调用真实书库；下面的分析均为系统示范，不署名给任何作者。历史金标准未修改。

## 同一个起始问题

“有 25 个人咨询了我的产品，但一个付费的都没有，是不是需求不成立？”

**需要避免的直接跳步（示意，不是旧答案原文）：**“25 人零付费，说明付费意愿弱。先换定位或降价。”它跳过了一个前提：对方是否真正收到过可购买的方案？没有这个前提，不能把尚未发生的测试当失败测试。

## 新流程的一条三轮分支

### 第一轮：先核实判断前提

❓ **Q1 — 是否真的卖过**：这 25 人是否收到过明确的价格、能得到什么，以及实际付款的方式？还是只咨询过想法？

问这个，是因为“没被邀请购买”和“面对明确方案仍拒绝”会走向不同分析。这里不推荐事实答案。

模拟用户：“只是聊过想法，还没报价。”

回应：“那目前能确认的是你还没测试购买，不能直接判需求失败。下一步先看有没有能兑现的方案，而不是先分析大家为什么嫌贵。”

### 第二轮：顺着刚刚明确的分支追问

❓ **Q2 — 可以兑现什么**：你现在能交付一份让对方看得懂、用得上的具体成果吗？如果有，是什么；如果还只有想法，也直接说就好。

模拟用户：“产品没做，但可以手工帮他们整理资料。”

回应：“这样就有了不先开发完整产品的备选路线。不过手工服务的价值和将来软件的价值并不完全相同，不能用前者的付款直接证明后者成立。”

### 第三轮：把决定留给用户

❓ **Q3 — 是否接受这条验证路线**：你愿意先尝试边界明确的手工服务，还是只想验证未来的软件？如果接受服务，最多愿意投入多少时间？

➡️ 如果你也想尽快了解对方愿意为什么结果付费，我倾向先试小范围服务；如果你的目标仅是可规模化软件，这个试验只能提供部分证据，不能代替软件验证。具体选择和投入由你决定。

模拟用户：“可以先服务，每天最多一小时，不想先开发。”

此时可以开始分析，不为了使用五轮额度再问两次。若第一轮回答是“已经报价而且对方理解了交付”，第二轮就应改问实际拒绝理由和替代方案，不沿用上面的“未报价”分支。

## 知识调用随之改变

| 内容 | 新的处理 |
| --- | --- |
| 用户事实 | 尚未报价；产品未开发；可手工整理资料；愿意先服务 |
| 约束 | 每天最多一小时；不先开发 |
| 仍未知 | 对方最看重的交付结果；明确方案下的实际购买反应 |
| 失效推断 | 零付费已证明需求弱；必须先降价 |
| 检索重点 | 购买测试是否成立、可兑现服务、交付范围与成本、服务验证与软件验证的区别 |
| 反证角度 | 手工服务可能不可复制；资料整理可能不是咨询者真正需要的结果 |

实际运行时把上述变化写入既有 user_update，再提交新的 prepare；随后真实检索、逐卡判断和验证，才能展示“《书名》｜作者｜知识名称”。不能给这份模拟表格配上没有查过的书目。

## 质询怎样改变行动

以下是系统检查示范，不是有书籍证据的真实圆桌。

- 初步主张：“先试付费手工服务，可以检验需求。”
- 质疑：“即使有人付费，也可能买的是定制劳动或信任，不是未来软件。你究竟验证哪个需求？”
- 裁决收窄：“先检验这类人是否愿意为明确结果付费，记录哪些价值来自标准化交付、哪些来自个人劳动；不据此直接宣布软件市场已成立。”
- 行动同步：“定义一个能在时间约束内兑现的成果、价格与服务边界，先确认对方理解再记录是否购买及拒绝理由。不承诺开发，不用打折或口头好评代替验证；若交付持续超时，先调整范围，不直接扩大获客。”
- 改判条件：“在理解方案、有实际购买机会的前提下仍反复拒绝，才进一步比较价值、价格、信任和目标人群；成交也只支持本次服务条件，不自动外推到软件。”

正式答案仍先给充分建议，再展示实际调用的书名、作者、原理、用户映射及关键交锋；这次升级改变的是判断路径，不是把回答缩成三轮问答。

产品回答末尾可以承接已知情况，例如：

> 继续和 AI 聊：请基于每天一小时、不先开发的限制，帮我设计一份能兑现的手工服务报价，并说明哪些结果能支持软件方向、哪些不能。
