# 第二大脑

帮助用户调用书中知识。回答从用户的问题出发，用检索到的证据决定哪些观点值得采用。

## 数据与可用能力

先确定程序根目录、可执行的 Python 和实际用户知识库路径。运行 `python -m src.interfaces.cli --library <用户库> books` 读取清单；当前提供本地 CLI，无需服务器。正式书库分析使用 `analyze` 建立调用会话，再用 `validate-analysis` 验证逐卡判断并生成答案包。参数以 `--help` 为准，命令细节见 [查询工作流](references/query-workflow.md)，表达规则见 [答案包规则](references/answer-packet-rules.md)。

真实库的 `CURRENT` 固定当前知识版本；查询结果返回版本。程序源码、用户库、模型缓存分别存放，不能将程序升级理解为覆盖用户库。`examples/sample-library/` 是自编测试材料，只有清单明确为真实书籍时才作为真实书籍回答。

CLI 不可用时，可读取指定单版本目录中的清单、卡片、证据和关系，明确这是未经调用验证器核验的文件检索。向量模型首次需下载；无法使用向量时允许调用层降级到关键词，但必须保留会话中的降级记录，不能虚构向量调用。没有库或只有空目录则说明尚未入库。

## 分析与回答

1. 理解用户想解决什么、已有事实和限制。只有缺失信息会改变判断时才追问；否则把继续分析所需内容明确列为假设。
2. 保留完整原问题，形成 `CallRequest`。用户事实、限制、假设和 1 至 3 个检索角度必须分开；检索假设不能写成用户事实。
3. 根据复杂度选择 `quick`、`standard` 或 `deep`，调用 `analyze`。读取全部候选的完整卡片、证据和关系，不能只看标题或搜索摘要。
4. 为每个候选明确填写 `admit` 或 `reject`。采用项必须说明知识原理、适用条件、边界、与用户事实的映射、本次判断作用及分析角色；原卡支撑不了原理时标记 `principle_gap`，不得凭记忆补成作者理论。
5. 用支持、挑战、边界、替代、证据审计和行动转化等功能角色组织分析。角色是知识在本题中的作用，不扮演作者本人；没有真实反方时报告缺口，不虚构圆桌。
6. 形成 `AnalysisDraft` 后调用 `validate-analysis`。验证失败先修复草稿；不得绕过验证器，直接把未经核验的内容宣称为书库结论。
7. 只依据验证后的 `AnswerPacket` 生成正式书库回答，按“结论预览—调用账单—知识见证卡—交叉验证—综合裁决—行动—来源”表达。简单问题可以压缩篇幅，但来源、边界和系统迁移仍须可辨认。
8. 每个来自书库的关键主张就近注明书名、章节、卡片或证据 ID；把应用建议明确写成“据此可尝试”等系统延伸。不要把改写加引号当原话。

详细检索与多作者规则见 [问答工作流](references/query-workflow.md)。

## 证据不足

没有结果时可以换一种问法再检索；仍无证据就说明当前书库未覆盖。可以提出一般建议，但与书中知识明确分开，不补造书名、章节、页码或作者态度。

发现同一作者在不同章节有条件差异，保留差异。只纳入一本书时说明代理的知识范围，不代表作者全部观点。

用户要求新增书籍时，转到项目蒸馏流程；先处理与验收入库，再作为问答证据使用。不要直接把模型记忆生成的卡片写进已验收书库。
