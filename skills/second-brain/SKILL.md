# 第二大脑

帮助用户调用书中知识。回答从用户的问题出发，用检索到的证据决定哪些观点值得采用。

## 数据与可用能力

先确定程序根目录、可执行的 Python 和实际用户知识库路径。运行 `python -m src.interfaces.cli --library <用户库> books` 读取清单；当前提供本地 CLI，无需服务器。正式书库分析使用 `analyze` 建立调用会话，再用 `validate-analysis` 验证逐卡判断并生成答案包。参数以 `--help` 为准，命令细节见 [查询工作流](references/query-workflow.md)，表达规则见 [答案包规则](references/answer-packet-rules.md)。

真实库的 `CURRENT` 固定当前知识版本；查询结果返回版本。程序源码、用户库、模型缓存分别存放，不能将程序升级理解为覆盖用户库。`examples/sample-library/` 是自编测试材料，只有清单明确为真实书籍时才作为真实书籍回答。

CLI 不可用时，可读取指定单版本目录中的清单、卡片、证据和关系，明确这是未经调用验证器核验的文件检索。向量模型首次需下载；无法使用向量时允许调用层降级到关键词，但必须保留会话中的降级记录，不能虚构向量调用。没有库或只有空目录则说明尚未入库。

## 分析与回答

1. 先利用已有对话和材料理解用户目标、事实和限制。只有缺失信息会改变判断时才追问；新问题通常3–5轮、最多5轮，信息够用或用户要求直接分析时提前结束，也可0–2轮。先读 [Grilling 分轮追问与判断检验](references/grilling-intake.md)，按决策依赖选择当前可问的问题，等待回答后重新组织分支，不预设五轮清单，不为凑次数追问。达到上限后基于已知信息与明确假设给出充分的条件式分析；确实无法判断的部分说明缺口，不硬下诊断。历史档案上限、计数与后续深化规则见问答工作流。
2. 保留完整原问题，形成 `CallRequest`。用户事实、限制、假设和检索角度必须分开；根据问题自由选择少量真正不同的视角，最多六个，不为凑数重复改写，检索假设不能写成用户事实。多轮问题默认使用 `intake-start/update/show` 持久化同一档案，准备后以 `analyze --problem` 编译请求；详见问答工作流。不要为同一问题另建档案重置计数。`goal` 是任务类型，真实目标单独记录为 `desired_outcome`。
3. 根据复杂度选择 `quick`、`standard` 或 `deep`，调用 `analyze`。读取全部候选的完整卡片、证据和关系，不能只看标题或搜索摘要。
4. 默认生成 `schema_version: 3` 的分析草稿，遵循项目根目录 `prompts/answer-orchestrator.v3.md`。先诊断用户表面问题、真正要解决的结果、关键未知和隐藏假设；原问题已经准确时可以保留，不强行为了“深刻”而改写。再为每个候选明确填写 `admit` 或 `reject`。采用项必须把知识为什么成立、如何影响判断讲清楚，并说明成立假设、适用条件、边界、与用户事实的索引映射、独立判断和误用风险。解释方式不固定，可按知识特点使用机制、推导、例子、类比、反例或权衡。每张采用卡另填 `adoption`，显式选择本次采用主张、证据与不采用范围，不能默认把整张卡判为已支持。
5. 把采用卡组织成服务本题的知识组，说明每组解决哪部分问题、书与书之间如何连接。先让入席卡各自独立判断，再用支持、反对、矛盾、削弱前提、互补和依赖组成论证关系。圆桌检查支持、反方、替代方案和证据审计；角色是知识在本题中的作用，不扮演作者本人；没有真实材料时报告缺口。
6. 形成 `AnalysisDraft` 后调用 `validate-analysis`。验证失败先修复草稿；不得绕过验证器，直接把未经核验的内容宣称为书库结论。
7. 允许基于已验证材料自由形成跨书综合、类比、待验证假设或用户未提出的新选项，但必须标明这是系统综合，绑定依据和验证需要，不能把模型推导署名给作者。没有可靠认知增量时如实说明，不强行制造新观点。
8. 只依据验证后的 `AnswerPacket` 生成正式书库回答，采用渐进分层：第一层是“结论—关键依据—立即行动”，用户只读这一层也能执行；充分解释建议的优先顺序、做法、取舍和适用条件，不限段落或条数，不把具体建议全部推到讲书之后。第二层按知识组，以“《书名》｜作者｜知识名称”展示采用卡、原理解释、知识关系和用户映射；第三层按“独立立场—交叉质询—主持裁决”展开知识议事过程，展示质疑怎样改变或限制建议，再给出改判条件、学会的方法、继续路径和来源账本。简单问题可以压缩篇幅，但来源、边界、改判条件和知识迁移仍须可辨认。
9. 回答结尾根据本轮未决问题提供可继续的方向，例如继续诊断、深入学习原理、继续找书、挑战当前结论或进入执行。不要只写“还有什么问题”，也不要固定凑满菜单；说明每条路径继续后会得到什么。AI 再推荐当前最值得继续的一条，并把一条用户可以直接发送的明确指令放在全文最后一行，格式为“继续和 AI 聊：……”；最后一行之后不再追加来源、注释或客套话。
10. 每个来自书库的关键主张就近注明书名、章节、卡片或证据 ID；把应用建议明确写成“据此可尝试”等系统延伸。不要把改写加引号当原话。
11. 出稿后检查答案与采用书目、条件裁决的一致性，并对照已认可样例检查建议深度、知识解释和实际交锋；不按固定字数、卡数或角色数判定质量。逐卡淘汰不能自动套用通用理由。格式校验和 Agent 自审不代替用户效果验收。

新版见证卡只以 `adopted_claim` 与本次选定证据为书库主张边界，`excluded_scope` 是不采用范围，不得作为正面依据。`original_card_ref` 仅供回看原卡审计，不代表整卡授权；不得从旧 `claim/reasoning` 自动补回内容。原理详解、系统综合和自由延伸保持充分并明确归属；旧v1/v2仍可显式读取作历史兼容，但不具备v3的采用隔离，不能混用。

详细检索与多作者规则见 [问答工作流](references/query-workflow.md)。

## 证据不足

没有结果时可以换一种问法再检索；仍无证据就说明当前书库未覆盖。可以提出一般建议，但与书中知识明确分开，不补造书名、章节、页码或作者态度。

发现同一作者在不同章节有条件差异，保留差异。只纳入一本书时说明代理的知识范围，不代表作者全部观点。

用户要求新增书籍时，转到项目蒸馏流程；先处理与验收入库，再作为问答证据使用。不要直接把模型记忆生成的卡片写进已验收书库。
